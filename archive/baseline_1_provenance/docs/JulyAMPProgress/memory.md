## RL walking plan (started 2026-07-17)

Adapt Isaac Lab's velocity-tracking locomotion env (Go2/ANYmal template) + PPO (rsl_rl). Do **not** build from scratch.

1. Real-values USD → `ArticulationCfg`: default standing pose (symmetric ±90° knees → must pick bend direction; front-heavy → feet forward under head), actuator model from servo specs (pending). Lock head/tail for v1; tail-for-balance is a later experiment (low inertia ratio ⇒ modest benefit).
2. Clone locomotion env: obs = base vel, gravity, joint pos/vel, last action, velocity command; actions = 12 joint position targets; rewards = velocity tracking + fall/energy/slip/limit penalties.
3. Domain randomization — copy Spot blog ranges: Kp/Kd/motor-strength factor 0.9–1.1, payload mass, CoM shift, friction, pushes. Extra important with hobby servos.
4. PPO on RTX 2070: ~1–2k envs, hours→overnight. MLP [512, otehr256, 128]. Later: ONNX export for sim2real (use ~70–80% stall torque, never unlimited).

## Improved-walking task (stage 2, 2026-07-17)

- Baseline `Bingo-Velocity-Flat-v0` learns to **drag, not walk**: inherited `feet_air_time` threshold 0.5 s is too long for a 2.5 kg robot (normal ~0.2 s step scores NEGATIVE → dragging is the optimum), and the all-zeros default pose can't be balanced.
- New separate task `bingo_rl/bingo_rl/improved_walking_cfg.py` (baseline files untouched): crouched default pose, air_time threshold 0.15, `feet_slide` −0.2, `is_terminated` −100 penalty, real fall detection (`root_height_below_minimum` 0.14 + `bad_orientation` 0.8), stage-1 forward-only command (lin_vel_x 0.2–0.4, no y/yaw, tracking std 0.2), randomization disabled. Runner `max_iterations` 1000, experiment `bingo_improved_walking`. Tasks: `Bingo-Improved-Walking-Flat-v0`, `-Flat-Play-v0`, `-StandTest-Play-v0`.
- **Joint axes (URDF):** `SP_J` (hip) & `knee` are `0 1 0` (+Y) for ALL 4 legs; only `SY_J` is mirrored L/R (`∓1 0 0`). So the *same* hip sign on all legs swings them together, not into a stance. **Verified crouch: `SP_J=-0.3, knee=+0.6` (hip NEGATIVE).** Positive hip (0.5/0.9) face-plants. Drives are weak — a mild crouch holds but deep (−0.5/1.0) sags → don't deepen without raising actuator stiffness.
- **Always run the stand test before a full run** (`--task Bingo-Improved-StandTest-Play-v0`, action scale 0 → holds default pose): render a settled frame, confirm it stands. First attempt trained 1500 iters and failed (action std rose 1.0→1.36, entropy 19.4, error_vel 0.6 — never converged) purely because the pose collapsed.
- Pose-sweep tool: `scratchpad/pose_preview.py` (renders candidate poses, reports settled base_z). Joint-name substrings for matching: `SY_J`, `SP_J`, `knee`.

## rev_3 asset + CLI-vs-GUI drive-gain gotcha (2026-07-18)

- `bingo_urdf_rev_3` = SolidWorks re-export with the **bl_knee mass fixed** (was 0.1273, now 0.1529, matching the other 3 knees). Raw export had `effort=0` and `package://` mesh paths → I made `bingo_urdf_rev_3_real_values.urdf` (relativized meshes, injected effort/vel 3/10 legs, 1.5/8 head-tail) and converted it via `scratchpad/convert_rev3.py` → `bingo_urdf_rev_3/urdf/bingo_scene_real_values_3/bingo_scene_real_values_3.usd`.
- **CRITICAL GOTCHA:** the CLI `UrdfConverterCfg` with `NaturalFrequencyGainsCfg(natural_frequency=25, damping_ratio=1)` produces drive stiffness **~55x WEAKER** than the Isaac Sim GUI URDF importer with the *same* nat-freq/damping settings. Measured: rev_1(GUI) knee k≈2.1 vs rev_3(CLI) knee k≈0.038. Result: rev_3 crouch collapsed in the stand test even though masses/pose were correct. The two importers compute nat-freq gains on different scales — do NOT assume they match.
- **Fix:** in `improved_walking_cfg.py`, `BINGO_IMPROVED_CFG` (deep-copied from `BINGO_CFG`) points `spawn.usd_path` at the rev_3 USD and **overrides actuator stiffness/damping with rev_1's measured per-joint values** (SY 1.15, SP 1.82, knee 2.10; damping 0.092/0.146/0.166; head_tail 1.5/0.12). This reproduces rev_1 dynamics + corrected mass, independent of the USD's (weak) authored gains. Read gains from any USD with `scratchpad/read_drives2.py` (pxr via AppLauncher).

## Gait-quality loop v3→v6 (2026-07-19)

- **Objective gait-eval harness** `bingo_rl/scripts/eval_gait.py` (run `CUDA_VISIBLE_DEVICES=1 ./isaaclab.sh -p eval_gait.py --task Bingo-Improved-Walking-Flat-Play-v0 --num_envs 64 --steps 400 --headless --device cuda:0`). Loads the latest checkpoint, **pins the command to straight forward 0.3 m/s**, and prints per-foot contact%, cadence(Hz), mean swing air-time, in-contact slip, plus base height/tilt/vx-tracking. This is the *precise* judge — the RecordVideo camera is fixed-wide so legs are too small to see. Frames for eyeballing: `ffmpeg -i output/bingo_flat_improved_vN.mp4 -vf fps=4 ...` then Read the PNGs. Record with `bash bingo_rl/scripts/record_vN.sh vN`.
- **v3 failure = learned tripod limp, NOT an asset bug.** Eval showed `fr_knee` 0% contact (never touched), base dragging at h=0.144 (vs 0.202 it *could* stand at, measured with action=0), 18° tilt, front-left skating (slip 0.45). Asset is symmetric (all 4 knees 0.153 kg, gains 1.15/1.82/2.10, limits match) — verified with `scratchpad/inspect_legs.py`. Root cause: tracking over-weighted (2.0, std 0.2) so PPO drags to nail velocity; gait terms too weak; `feet_air_time` only *rewards* feet that touch so a permanently-lifted foot is never punished.
- **v4 fix (tripod → all 4 feet cycling):** added custom `air_time_over` penalty (module-level fn in `improved_walking_cfg.py`, charges `current_air_time` above 0.35 s → kills permanently-lifted legs), raised `low_base` floor 0.14→0.165, `flat_orientation_l2` −1.0→−2.5, `feet_air_time` 0.1→0.25, `feet_slide` −0.2→−0.4, tracking 2.0/std0.2 → 1.5/std0.25. Result: h=0.185, tilt 2°, fr 0%→43%. Left/right lean remained.
- **v5:** re-enabled bidirectional turning (`ang_vel_z (-0.5,0.5)`, `track_ang_vel_z_exp` 0.5) as a symmetry driver. fr 43%→61%, but back-right still only ~25% grounded (flutters at 2.6 Hz).
- **v6:** re-enabled domain randomization the staged plan had switched off (std Go2 has it, Bingo lacked it): `push_robot` reconstructed (interval 4–7 s, vel ±0.3 x/y, yaw ±0.4), varied reset (`reset_robot_joints` scale 0.9–1.1 + vel ±1.0, `reset_base` velocity ±0.3). Fixed the back-right foot (25%→41%) and **unified cadence** (br's 2.6 Hz flutter gone, all feet ~1.76 Hz), but PPO *relocated* the asymmetry — front-left became a static prop (85% grounded, 0.077 s air). Lesson: randomization reduces but does not remove emergent L/R asymmetry; it just moves which leg is sacrificed.
- **v7 (SOLVED — natural symmetric trot):** added `contact_time_over` penalty (module fn, mirror of `air_time_over`: charges `current_contact_time` above 0.35 s, weight −1.0). The air-cap + contact-cap pair forces *every* foot onto a bounded lift/plant cycle, so no leg can be parked up (tripod) or down (prop) — and it needs **no left/right index mapping**, so it fixes whichever leg PPO tries to sacrifice. Result: all 4 feet 52–62% contact (was 24–85% in v6), cadence locked 2.0 Hz, air 0.18–0.23 s, slip 0.06–0.10, base h 0.187, tilt 2°, vx err 0.018, reward 34, 99.6% time_out. Video `output/bingo_flat_improved_v7.mp4` shows a tall, level, coordinated four-leg trot.
- **Key insight:** the symmetric-cap approach (bound both max air-time and max contact-time per foot) is a cheap, robust alternative to PPO mirror-symmetry augmentation for eliminating one-legged-sacrifice gaits — no obs/action mirror function to get wrong.
- **Training loop:** each version = edit `improved_walking_cfg.py` → `CUDA_VISIBLE_DEVICES=1 ./isaaclab.sh -p train.py --task Bingo-Improved-Walking-Flat-v0 --num_envs 4096 --headless --max_iterations 1000 --seed 0 --device cuda:0` (~20 min on 4090) → `eval_gait.py` → `record_vN.sh`. Healthy training: episode length climbs to ~1000, ~99% time_out, reward v4≈24 / v5≈32 / v7≈34.

## Rough-terrain walking (blind, warm-started — 2026-07-19)

- **Task** `Bingo-Improved-Walking-Rough-v0` / `-Rough-Play-v0` in `improved_walking_cfg.py` (`BingoImprovedRoughEnvCfg`). Inherits the v7 flat gait design, re-enables scaled procedural terrain + the `terrain_levels_vel` curriculum, stays **blind** (no height scanner → obs stays 58, identical to flat) so the v7 checkpoint warm-starts directly.
- **Terrain scaling is the #1 make-or-break** for a 0.2 m robot. Stock `ROUGH_TERRAINS_CFG` (steps 0.05–0.23 m, boxes 0.2 m, slopes 0.4 rad) is sized for a 0.5 m ANYmal → instant faceplant. `BINGO_ROUGH_TERRAINS_CFG` uses tiny obstacles, **no stairs**: flat 0.2 / random_rough noise 0.005–0.03 (0.4) / boxes h 0.01–0.04 (0.2) / gentle slopes 0–0.15 rad (0.1+0.1). `curriculum=True` → row 0 = easy end of each range, top row = hard end.
- **Gotcha:** `MeshRandomGridTerrainCfg.grid_width` must NOT evenly divide `size` (8.0) or it errors `"Border width must be greater than 0"` — border = `size - int(size/grid_width)*grid_width`. 0.25 → border 0 (fails); **use 0.3** → border 0.2.
- **Warm-start mechanism:** `get_checkpoint_path` only searches within `logs/rsl_rl/<experiment_name>`, so to resume across experiments I copied v7's `model_999.pt` into `logs/rsl_rl/bingo_improved_rough/warmstart_v7/`, then trained with `--resume --load_run warmstart_v7 --checkpoint model_999.pt`. rsl_rl restores the iteration counter (starts at 999) and runs `max_iterations` MORE (→ 2499). **Caveat:** `warmstart_v7` sorts alphabetically AFTER the timestamped run, so `eval_gait`/`play` with default `load_run=".*"` grab the OLD v7 copy — always pass `--checkpoint <new run>/model_2498.pt` explicitly for rough eval/record.
- **Rough-only reward relaxations** (flat penalties that fight terrain): `flat_orientation_l2` −2.5 → −1.0 (body must tilt on slopes); `low_base` floor 0.165 → 0.10 (world-height floor false-fires in dips/behind bumps — real falls still trip `bad_orientation`/`base_contact`); air/contact caps 0.35 → 0.45 (terrain forces variable step timing); friction randomized 0.4–1.0 / 0.3–0.9 (was fixed).
- **Result (1500 warm-started iters ≈ 35 min):** reward 0.35→28, ep_len ~1000, 98.6% time_out, base 0.206, tilt ~4°, vx err 0.049, all 4 feet cycling & retiming to terrain (contact 46–68%, cadence 1.5–2.4 Hz). Video `output/bingo_rough_v1.mp4`. The v7 policy already walked the scaled terrain blind out-of-the-box (Step-0 sanity check) — confirming terrain wasn't too hard before committing the run.
- **Curriculum note:** mean `Curriculum/terrain_levels` climbed slowly over the run (0.66 @ iter1010 → ~0.9 mid-run → **1.07 @ iter2498, still gently rising**) — it never plateaued hard, but promotion is slow (turning commands cut net forward distance, and the deliberately-gentle terrain is walkable even at top rows, so the curriculum has little pressure to advance). The robot is fully competent at the levels it reaches; the low number reflects gentle terrain + slow promotion, not a failure. To push harder terrain later: raise obstacle ranges and/or bias commands more forward; or add the height-scan obs (breaks the warm-start, needs more iters) for real stairs.
- **Final training tail (2026-07-19, `logs/rsl_rl/bingo_improved_rough/2026-07-19_11-53-00/model_2498.pt`):** reward stabilized 27–28, ep_len ~1000 (frequently hitting the 1000 cap), terminations 98.6% time_out / 0.66% low_base / 0.72% bad_orientation / 0% base_contact — i.e. the robot essentially never actually falls; the rare non-timeouts are shallow dips, not crashes.

## AMP dog-style imitation (2026-07-21, DONE — see round 2 below for the final gait)

Goal: make Bingo trot like a real dog via Adversarial Motion Priors (AMP), driven by dog MoCap. Plan in `AMP_Plan.md`, brainstorm in `MimicKitMotion.md`. **Outcome: working clean diagonal dog trot — final deliverable `output/bingo_amp_FINAL.mp4`, config in "FINAL WORKING RECIPE" under round 2.** This section = how the pipeline was built + the first-pass tuning; the round-2 section = the gait-quality fixes that produced the final result.
- **Environment reality:** the ONLY AMP in this IsaacLab is `direct/humanoid_amp` — **Direct workflow + skrl's AMP agent + `.npz` motion format**. skrl was not installed (`pip install "skrl[torch]"` → 2.1.0). There is NO Go2/quadruped AMP example locally; the known-good reference is Humanoid-AMP-Walk. `isaaclab_mimic` = manipulation datagen, unrelated. v7 is manager-based+rsl_rl → AMP is a **clean rebuild, no warm-start from v7** (different RL lib + workflow).
- **Pre-flight leg-axis finding (important, verified via analytical URDF FK):** the uniform default pose `.*_SP_J:-0.3 / .*_knee:0.6` is WRONG because rev_3's right-leg joint axes are flipped. Correct **bilateral sign map** (canonical→URDF): SP = [fl+1, bl+1, **fr−1**, br+1]; knee = [fl+1, bl+1, **fr−1**, **br−1**]. So symmetric default = fl(SP−0.3,kn+0.6) bl(SP−0.3,kn+0.6) **fr(SP+0.3,kn−0.6) br(SP−0.3,kn−0.6)**. `br_knee` inverted (axis `0 1 0`, given +0.6, should be −0.6) = the user's "back-right slightly inverted." This sign map is what the retargeter uses so left/right are true mirrors. Check script: `bingo_rl/scripts/check_leg_symmetry.py` (dynamic test is confounded by weak-drive sag; the analytical FK is the clean judge).
- **Data:** Peng `motion_imitation` dog clips (`dog_trot.txt`, `dog_pace.txt`) via raw.githubusercontent — Laikago-retargeted, 60fps, frame=[root_pos(3),root_quat xyzw(4),12 joints]. `dog_walk`/`dog_spinl` 404. Origin: Zhang 2018 dog MoCap (AI4Animation), research-license.
- **Retargeter** `bingo_rl/scripts/retarget_dog_to_bingo.py` (pure numpy): joint-space affine map dog leg→Bingo leg (FR→fr, FL→fl, RR→br, RL→bl), centered on Bingo crouch, amplitude-scaled to joint limits, **× the sign map**. Feet (=knee-link origins) + root filled by analytical FK. Only the ref body (`origin`) + 4 feet (`*_knee`) are actually used by the loader, so no sim-FK needed. Validated numerically = **textbook trot** (diagonal pairs in-phase fl·br +0.73/fr·bl +0.74, lateral/front-back anti-phase −0.85/−0.72, clean L/R mirror). `--fwd_speed` overrides root speed.
- **AMP env** (Direct workflow) in `bingo_rl/bingo_rl/amp/`: `bingo_amp_env.py` + `_cfg.py`, task `Bingo-AMP-Trot-Direct-v0`, agent cfg `agents/skrl_amp_cfg.yaml`. Mirrors humanoid_amp; obs=AMP-obs=**49** (`dof_pos12+dof_vel12+root_h1+quat_tan_norm6+root_lin3+root_ang3+4feet×3`), action=12. **Bingo has 17 joints (12 legs+5 head/tail); must restrict actions/obs/reset to the 12 leg DOFs** via `robot_ctrl_indexes` (head/tail held at default) — the humanoid actuated all its joints, Bingo can't. Reuses `BINGO_IMPROVED_CFG` (rev_3 USD + measured gains) with the symmetric default pose. Train/play = **copies of IsaacLab's skrl `train.py`/`play.py`** (`scripts/train_amp.py`, `play_amp.py`) with `import bingo_rl` injected (bingo_rl isn't pip-installed). Run: `CUDA_VISIBLE_DEVICES=1 ./isaaclab.sh -p bingo_rl/scripts/train_amp.py --task Bingo-AMP-Trot-Direct-v0 --algorithm AMP --headless --num_envs 4096 --max_iterations 3000`. Logs → `IsaacLab/logs/skrl/bingo_amp_trot/<run>/` (skrl saves `agent_<step>.pt`+`best_agent.pt` every ~4800 steps; scalars via tensorboard, `Reward/Total reward (mean)` here).
- **KEY tuning finding:** pure AMP (task_reward_scale 0, style 2.0 — the humanoid default) → Bingo learns the dog trot RHYTHM but **trots IN PLACE** (survives full 300-step episodes but doesn't translate; visible by same grid position across frames). The AMP obs has root_lin_vel but the discriminator doesn't enforce travel strongly (24/49 obs dims are joint pos/vel — a standing trot matches those). **Fix = add a velocity-tracking task reward.**
- **Reward shape matters:** an `exp(−(vx−target)²/σ)` reward left a comfortable ~0.37 floor for standing → still trotted in place. Switched to a **monotonic** reward `clamp(vx/target, 0, 1)` (standing→0, target→1) — this reliably forces travel. `_get_rewards` in `bingo_amp_env.py`.

## AMP gait-quality fixes — dragging back legs, veer, bound (2026-07-21, round 2)

User feedback on the first AMP trot (v6/final): back legs **drag straight out behind** (not stepping), robot **veers/"turns in"**, and front-pair/back-pair move together. Root cause: the AMP "feet" are **knee joints that barely move vertically**, so the discriminator can't tell a stepping leg from a dragging one, and the task reward (velocity) is happy to get forward motion from front legs + back drag. Fix = **add contact-sensor-based gait shaping to the task reward** (the v7 idea, inside the Direct AMP env). Added `ContactSensorCfg(prim_path=".*_knee", track_air_time=True)` to the env; reward factors multiply the velocity reward (all kept in [0,1]).
- **Iteration journey (each ~40 min, whack-a-mole — every fix exposed the next):**
  - air/contact-time **caps, unbounded** `exp(-2·over)` → reward → 0 everywhere (a dragging foot's contact time grows huge) → **collapse**. Fix: **bound** the over-limit (`clamp(...,max=1.5)`) and soften scale → floor ~0.35, gradient preserved.
  - caps (bounded) + yaw penalty → back legs cycle & goes straight, but **crouches to a 0.12 belly-crawl** (crouching cycles feet faster within the caps).
  - + **height**: raise `termination_height` 0.10→0.15 (hard floor, no belly-crawl) and a `height_factor = exp(-8·max(0.18−h,0))` → tall (0.197) & legs engaged, **but drifts to a BOUND** (front pair together, fl·fr +0.71) — the generic "all feet cycle" caps don't enforce diagonal phase, so the task reward picks a fast tall bound and overrides the AMP trot.
- **THE FIX (v9, works):** replace the generic caps with an **explicit diagonal-trot-phase reward** from contact booleans `[fl,fr,bl,br]`: `trot_score = 0.25·[(fl==br)+(fr==bl)+(fl≠fr)+(fl≠bl)]` = **1.0 for a trot, 0.25 for a bound or pace**; `trot_factor = 0.2+0.8·trot_score`. Final reward = **`vel_rew × trot_factor × height_factor`** (velocity × diagonal-trot × tall). Drop the yaw term (a symmetric trot doesn't veer). per_step ceiling for a bound is ~0.44 vs ~0.95 for a trot, so the reward level itself signals the gait.
- **Result (v9 completed 48k, `logs/skrl/bingo_amp_trot/2026-07-21_20-00-11_amp_torch/checkpoints/agent_48000.pt`, MOVING checkpoint):** clean diagonal dog trot — base 0.192 (tall), tilt **0.008** (dead level), vx 0.568, **back legs step with real lift** (bl/fr vert 0.019–0.021), and **near-perfect trot signature on the moving policy**: fl·br +0.98, fr·bl +1.00, fl·fr **−0.98** (front legs anti-phase, no bound), fl·bl −0.97. **Definitive video `output/bingo_amp_FINAL.mp4`.** Fixes the drag/veer/bound feedback. ## v9→v15 factual changelog — what we changed after v9 and why we expected it to work

Plain record of each iteration: the exact change, the reasoning going in, and the measured result. (v9 = the kept best: single `bingo_trot.npz`, reward `vel×trot_factor×height`, task/style 1.5/1.5, knee-hinge feet, flat root. Eval: vx 0.568, tilt 0.008, fl·br +0.98.)

- **v10 — add foot lift + body bob.** *Changed:* in the retargeter, replaced the knee-hinge "foot" with the shank TIP (SHANK_LEN 0.12, computed via real knee angle) and matched the same offset in `bingo_amp_env.py` obs; injected the dog clip's root pitch/roll (G_ROOT_ROT 0.5) + vertical z-bob into the reference. *Why we expected it to work:* v9 read as "mechanical"; measurement showed the reference feet moved only ~8mm vertically and the root was a flat glide with a frozen quaternion — three AMP channels were dead constants.
